## 2. Сначала исправь достоверность интерфейса

### Оперативная обстановка

В `app/[locale]/page.tsx` ошибка `fetchHome` превращается в `EMPTY_HOME`. Верхний AlertBanner учитывает `unavailable`, но блок «Оперативная сводка» проверяет только `data.alerts.count` и при нуле выводит `home.ops.noneText`: «Активных предупреждений нет. Обстановка штатная». Получается противоречие при отказе CMS.

Исправь все зависимые блоки: подтверждённое отсутствие предупреждений, наличие предупреждений, недоступность данных и устаревшие данные должны быть различимы. При недоступности показывай нейтральное сообщение и доступный контакт экстренной помощи. Не подменяй отсутствие данных зелёным статусом. Добавь регрессионную проверку именно сценария отказа `/home`.

Если API предоставляет достоверное время обновления обстановки, показывай его с понятной временной зоной. Не используй время рендера как время обновления сведений. Если такого поля нет — опиши требуемое расширение API. ISR сам по себе не обновляет уже открытую вкладку: оцени потребность в обновлении статуса при возвращении на вкладку, не добавляя без необходимости частый polling всей страницы.

### Экстренная помощь и приёмная

На главной карточка «Сообщить о происшествии» ведёт в `/contacts`, где находится обычная электронная приёмная. Раздели обещания интерфейса:

- Экстренная помощь — существующая заметная ссылка `tel:112`.
- Несрочное обращение — «Написать обращение» / «Электронная приёмная», ссылка непосредственно на `/{locale}/contacts#reception` и соответствующий якорь у формы.
- Возле формы кратко поясни, что она предназначена для несрочных обращений. Существующие официальные сроки не меняй без подтверждённого источника.

Сохрани существующую серверную валидацию, сообщения 422, согласие и номер обращения. Проверь фокус на первой ошибке и объявление результата скринридером; добавь только недостающее. Никаких реальных тестовых отправок в CMS.

### Пустые состояния и ссылки

- `fetchSearch` сейчас возвращает одинаковый пустой результат при отсутствии совпадений и отказе API. Сделай различимые состояния «ничего не найдено» и «поиск временно недоступен», сохраняя введённый запрос и предлагая осмысленное следующее действие. Проверь аналогичные состояния каталогов.
- «Открытые данные» в `lib/copy/common.ts` ведёт на `#`, хотя в документах уже есть фильтр `type=open_data`. Направь ссылку на существующий локализованный каталог с этим фильтром, проверь все три языка.
- Исправь несоответствие подписи `press@khf.tj` и перехода в `/contacts`: либо реальный подтверждённый `mailto:`, либо честная подпись «Контакты пресс-службы».
- Сделай телефонные номера в футере ссылками `tel:`, адреса email — `mailto:` там, где это контакты, а не просто упоминания.
- Локально видны тестовая новость, латинский текст и демонстрационные PDF. Отрази это в списке подготовки контента к запуску. Не маскируй тестовые записи фильтрацией по словам в заголовках и не подменяй содержимое выдуманными публикациями.

## 3. Обнови визуальную систему

Основной стиль — сдержанный официальный портал с ясной типографикой и заметными действиями. Работай через токены `app/globals.css` и общие компоненты, а не разрозненные inline-исключения.

- Осветли общий холодный фон: ориентир `#F5F7FA` вместо текущего `#E7ECF1`, поверхности карточек — белые, основной текст — тёмный графит. Это стартовые значения: окончательные пары проверь по контрасту в обеих темах.
- Для фона достаточно сплошной заливки или очень слабого статичного CSS-градиента. Не добавляй фоновые фотографии, видео, шум, анимированные частицы и тяжёлые декоративные изображения.
- Снизь визуальный вес `.blueprint`: тонкая граница, небольшой радиус, минимальная тень. Не оформляй каждый текстовый блок одинаковой рамкой и тенью. Разделяй секции отступами; акцентные полосы оставь там, где они обозначают приоритет.
- Сохрани тёмную служебную полосу и строгий футер. Сине-серый акцент используй для обычных действий; красный — для 112 и критических предупреждений; цвета опасности должны оставаться семантическими.
- Сохрани Fira Sans и Fira Sans Condensed, включая таджикские символы. Основной текст ориентировочно 16–18 px, пояснения 14–15 px; не используй 11–12 px для значимых действий, статусов и инструкций. Condensed и uppercase применяй умеренно, прежде всего для коротких заголовков.
- Для длинных статей и инструкций настрой комфортную длину строки порядка 65–75 символов, line-height 1.55–1.7 и последовательные отступы. Не увеличивай шрифты ценой переполнения таблиц или обрезки заголовков.
- Введи согласованную шкалу отступов и единые состояния кнопок/полей: default, hover, focus-visible, disabled, loading, error. Для основных touch-элементов целевой размер 44×44 px; это требование удобства данного проекта.
- Секционная нумерация `01 / ...` сейчас пропускает номер, когда условный блок предупреждений скрыт. Убери декоративную нумерацию либо формируй последовательность из реально показанных разделов. Название раздела должно оставаться главным ориентиром.
- Сохрани верхний статус и нижнюю сводку, но убери смысловое дублирование: верхний блок сообщает срочное состояние, нижний даёт полезную сводку и переход к деталям. Не добавляй неподтверждённые цифры ради заполнения места.

## 4. Мобильные сценарии и внутренние страницы

- На мобильном `/documents` сейчас таблица из шести колонок сжимает название до узкого столбца, а файл скрывается за горизонтальным скроллом. На узких экранах показывай документы карточками: полное название, тип, номер/дата при наличии, доступные языки, формат/размер и явная кнопка скачивания. На desktop сохрани таблицу. Сведения должны совпадать, скрытое представление не должно дублироваться для скринридера. При отсутствии файла показывай понятное состояние вместо одного тире.
- В мобильных новостях и документах фильтры занимают несколько строк до результата. Сделай более компактное адаптивное представление: при необходимости native select или доступный раскрываемый блок, видимый активный фильтр, число результатов при наличии данных и сброс. Сохрани GET-формы/ссылки, URL, пагинацию, работу Back/Forward и базовый сценарий без JavaScript.
- Улучши заметность поиска и его focus-состояние; не превращай заголовок страницы в тесный ряд с мелким подзаголовком. На мобильном подзаголовок можно перенести под h1.
- Сохрани доступность 112 в существующей липкой шапке. Проверь меню, поиск, переключение языков и отсутствие перекрытия контента при прокрутке и увеличении текста.
- В слайдере сохрани текущие клавиатуру, свайп, ручную паузу и reduced motion. Проверь длинные заголовки и комбинации с фотографией/без неё. При смене слайда не должны прыгать соседняя карточка президента и следующие секции. Останавливай автопрокрутку в скрытой вкладке и вне видимой области. Не предзагружай все слайды.
- На карте поддерживай понятную легенду, текстовые названия состояний и доступный список регионов. Не кодируй смысл только цветом. Проверь тач и клавиатуру, сохрани полезное текстовое представление при проблемах с графикой.
- В длинных инструкциях добавь компактную навигацию по существующим разделам, если её нет. Не переписывай официальные правила поведения и не скрывай ключевые действия за обязательными аккордеонами.
- Избегай крупных декоративных заглушек вроде «Фото пресс-службы», если реального изображения нет: используй содержательную текстовую компоновку. Не трогай фотографию президента.
- Проверяй длинные строки и таджикские символы на всех изменённых компонентах. Все новые UI-тексты должны иметь версии RU/TJ/EN.

## 5. SEO и семантика

- `SectionHeader` в `components/public/ui.tsx` всегда выводит h3. Сделай уровень заголовка явным: основные секции страницы — h2, вложенные — h3. Сохрани существующий главный h1; в критическом состоянии главной AlertBanner добавляет ещё один h1 — приведи структуру к одному основному заголовку без изменения визуального приоритета предупреждения. Семантика не должна зависеть от размера шрифта.
- В `app/robots.ts` поиск закрыт через `Disallow`, а на странице поиска задан `noindex`. Для применения noindex робот должен иметь возможность прочитать страницу. Согласуй правила: оставь noindex для внутреннего поиска и доступ к его HTML, исключение из sitemap сохрани. Не ослабляй ограничения для служебного API.
- Проверь политику query-параметров. Сейчас metadata новостей учитывает `page`, но игнорирует `category` и `q`. Свободный поиск внутри каталога — noindex; обычная пагинация — self-canonical. Для полезных индексируемых категорий сохраняй category в canonical и согласованных языковых альтернативах; технические/комбинированные фильтры обрабатывай по документированной политике, без противоречивых сигналов.
- `buildAlternates` и sitemap механически объявляют все три языка. На локальной `/en/news` часть материалов отображается по-русски. Проверяй наличие настоящего перевода, а не только HTTP 200 или одинакового slug. В hreflang и локализованный sitemap включай только реально опубликованные версии, обеспечь взаимность ссылок. Используй данные CMS о доступности переводов; не определяй язык регулярным выражением по буквам. Если контракта недостаточно — сформулируй точные необходимые поля/API и не объявляй задачу завершённой.
- Для отсутствующего перевода показывай честное сообщение и ссылку на доступную версию; не выдавай русский fallback за полноценную английскую публикацию.
- `siteUrl()` сейчас откатывается к localhost. Для production проверь обязательный публичный HTTPS origin, корректность canonical, og:url, JSON-LD и sitemap. Сборка production с отсутствующим/некорректным адресом должна сообщать понятную ошибку; локальный режим должен продолжать работать.
- Сохрани существующие GovernmentOrganization, NewsArticle и BreadcrumbList; проверь их соответствие видимому содержимому. Не добавляй фиктивные FAQ, авторов, рейтинги и даты. `dateModified` и sitemap `lastModified` добавляй только из достоверного поля CMS, не из текущего времени или даты публикации по умолчанию.
- Добавь общую OG-картинку портала для страниц без обложки и локализованные метаданные. Существующие реальные обложки материалов имеют приоритет. Проверь реальные preview URL и доступность изображений для внешнего робота, без внутренних localhost-адресов.
- Сохрани корректные 404 и различение 404/ошибки CMS. Проверь sitemap при частичном отказе API: сейчас `fetchSlugs` возвращает пустой массив, что может превратить временный сбой в урезанную карту сайта. Предпочитай последнюю успешную версию и явную обработку ошибки в рамках текущей модели кэширования.

## 6. Производительность: только проверяемые изменения

- Перед оптимизацией зафиксируй baseline на production build с доступной CMS и репрезентативным контентом: главная с изображениями, новости, длинная статья, документы, карта, контакты. Восстанови те же условия для сравнения после изменений. Не сравнивай пустую fallback-страницу с полной.
- Используй существующие `bundle:report`, Lighthouse-скрипты и бюджеты. Не понижай действующие пороги, не меняй метод throttling ради красивого балла. Сохранённые 99/100 — ориентир, а не доказательство текущего результата.
- У карты уже есть dynamic import, но она сразу монтируется на главной. Проверь network trace: если код и вычисление геометрии выполняются задолго до появления карты, отложи монтирование до приближения к viewport, оставив стабильный размер и SSR-список регионов. На `/map`, где карта — основное содержимое, не добавляй такую задержку. Учти документированную в компоненте проблему прежнего `ssr:false`.
- Проверь реальный LCP на desktop/mobile. Фото президента сейчас preload-ится безусловно, а на мобильном находится после слайдера; первый слайд с фото тоже использует preload. Подбери согласованную стратегию `preload` / `loading` / `fetchPriority` по документации Next 16, без конкурирующей массовой предзагрузки. Расположение блоков не меняй.
- Проверь `sizes` по фактической ширине колонок; например, фото внутри слайдера занимает только 42% его desktop-ширины, а подсказка сейчас 420 px. Оптимизируй скачиваемый размер без потери видимого качества. Сохрани lazy-loading изображений ниже первого экрана и резервирование их геометрии.
- `ImageSlot` является Client Component в том числе ради определения языка. По отчёту бандла оцени серверный вариант для статичных случаев с передачей локали через props. Не делай массовый рефакторинг ради формального сокращения числа client-компонентов.
- Сохрани два существующих компактных локальных WOFF2. Не добавляй внешние шрифтовые запросы и лишние начертания без необходимости.
- Не увеличивай общий TTL данных предупреждений ради Lighthouse. Сохрани адресную ревалидацию и согласованные состояния при сбоях CMS.
- RUM уже реализован через `WebVitalsReporter` → `/api/vitals` → CMS. Проверь конфигурацию, доставку и возможность агрегировать p75 по типу страницы, языку и устройству. При отсутствии доступа к production честно зафиксируй ограничение. Не собирай содержимое форм и поисковых запросов.
- Цели для полевых данных: LCP ≤ 2.5 s, INP ≤ 200 ms, CLS ≤ 0.1 на p75 отдельно для mobile/desktop. Сохрани более строгие существующие лабораторные бюджеты проекта. Не выдавай Lighthouse TBT за измеренный INP.

## 7. Проверка и результат

Работай небольшими законченными этапами. После каждого важного визуального изменения проверяй браузер, не ограничивайся JSX и скриншотом только первого экрана.

- Снимки до/после: главная, документы, новости, статья, инструкция, контакты, карта; light/dark; ширины 360, 390, 768, 1024, 1440 px. Полную матрицу всех страниц проходить необязательно: выбери репрезентативные шаблоны, но защищённые блоки главной проверь на всех указанных ширинах.
- Подтверди сохранение расположения слайдера и карточки президента, порядка на mobile и отсутствие скачков при смене слайда.
- Проверь keyboard/focus, 200% zoom, reduced motion, длинные тексты, доступность контраста и размеры целей нажатия. Не объявляй автоматический балл axe полной проверкой доступности.
- Добавь целевые регрессионные тесты на недоступную обстановку, семантику заголовков, robots/noindex, локализованные alternates и сохранение состояния фильтров. Визуальные изменения проверяй в браузере; не заменяй это тестами, которые только ищут CSS-классы в исходниках.
- Запусти релевантные существующие lint/typecheck/unit/e2e/a11y и production build; затем сопоставимый performance-прогон. Не выполняй отправку реальных обращений, публикацию или деплой.
- В конце представь: что изменилось для посетителя; список файлов; скриншоты до/после; baseline и итоговые показатели с условиями измерения; пройденные проверки; нерешённые зависимости CMS/контента. Не заявляй рост поисковых позиций без данных после запуска.

Выполни реализацию доступного объёма работ, а не только составь очередной план. При недостатке данных не подменяй их предположениями; сделай независимые улучшения и чётко выдели оставшиеся зависимости.
