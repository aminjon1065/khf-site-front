# Запросы на расширение контракта CMS

Изменения, которые **нельзя выполнить в репозитории фронтенда**: нужны новые
поля или гарантии от `khf-site-cms` (`/api/v1`). Каждый пункт — самостоятельное
задание с точной формулировкой, обоснованием и тем, что фронтенд сделал до
появления поля.

Основание — реализация UI/UX/SEO-задания 16 сентября 2026 года. Контракт сверен
по `openapi/openapi.json` этого репозитория.

---

## A-1. Время актуальности оперативной обстановки

**Что добавить.** В `ApiHome.alerts` и в `ApiAlertsActive` — поле времени, на
которое обстановка достоверна:

```jsonc
"alerts": {
  "state": "calm",
  "count": 0,
  "updated_at": "2026-09-16T09:42:00+05:00",   // NEW: ISO 8601 со смещением
  "regions": [ /* … */ ],
  "items":   [ /* … */ ]
}
```

Требования к полю:

- ISO 8601 **со смещением зоны** (`+05:00`), не «наивная» дата: портал
  показывает время в понятной посетителю зоне, и `Asia/Dushanbe` должен
  следовать из самого значения;
- смысл — «на какой момент сведения актуальны» (последняя сверка состояния
  предупреждений), **а не** `updated_at` строки в БД и не время ответа API;
- поле обязательное в ответе, даже когда `count = 0`: «предупреждений нет по
  состоянию на 09:42» и «предупреждений нет неизвестно с какого момента» —
  разные утверждения.

**Зачем.** Портал ЧС обязан отвечать на вопрос «насколько свежая эта тишина».
Сейчас достоверного ответа нет ни в одном поле.

**Что фронтенд сделал без этого поля.** Время рендера как время сведений
**не используется** — это было бы ложью (страница отдаётся из ISR-кэша и может
быть старше минуты). Вместо этого:

- «Оперативная сводка» различает четыре состояния: есть предупреждения, их
  подтверждённо нет, данные недоступны, данные могли устареть;
- открытая вкладка при возвращении фокуса тихо перезапрашивает маршрут
  (`RefreshOnVisible`), показывая на время запроса пометку «данные могли
  устареть» — без опроса по таймеру.

**Что появится после.** Строка «Обстановка на 09:42 (UTC+5)» рядом со сводкой и
в детальных карточках предупреждений.

## A-2. Достоверная дата изменения материала (`dateModified`)

**Что добавить.** В `ApiNewsItem` (и по возможности в `ApiInstruction`,
`ApiPageDetail`, `ApiProject`) — время последней содержательной правки:

```jsonc
"datetime":   "2026-03-24T10:00:00+05:00",   // публикация, есть сейчас
"updated_at": "2026-04-02T14:15:00+05:00"    // NEW: правка текста материала
```

Требования:

- только **содержательные** правки текста/полей материала; пересохранение без
  изменений, пересчёт счётчика просмотров и миграции поле менять не должны;
- `null`, если материал не правили после публикации, — тогда фронтенд поле
  просто не выводит;
- `ApiPageDetail.updated_at` уже есть и используется в `modifiedTime`; нужна
  та же гарантия смысла (правка текста, а не любое касание строки).

**Зачем.** `NewsArticle.dateModified` и `<lastmod>` в `sitemap.xml` —
сигналы свежести. Выводить их из даты публикации или из текущего времени
означает сообщать поисковику неправду о материале.

**Что фронтенд сделал без этого поля.** `dateModified` в JSON-LD **намеренно
опущен** (см. комментарий в `components/public/JsonLd.tsx`), а `lastModified` в
`sitemap.xml` не выставляется вовсе. Пустое поле честнее выдуманного.

## A-3. Явный признак наличия перевода

**Что добавить.** В детальные DTO — список локалей, в которых материал
действительно опубликован:

```jsonc
"available_locales": ["ru", "tg"]   // NEW, коды API (tg, не tj)
```

**Зачем.** Сейчас признак приходится выводить косвенно — из
`/slugs/{type}?locale=`, то есть три дополнительных запроса на страницу
(они разделяют кэш, но это обходной путь, а не контракт). Прямое поле:

- убирает зависимость от того, что `/slugs` продолжит означать именно
  «доступные в этой локали»;
- позволяет отличить «перевода нет» от «список slug'ов не получен».

**Что фронтенд сделал без этого поля.** `availableLocalesFor(type, slug)`
(`lib/api.ts`) собирает локали из `/slugs/{type}` по каждому языку; при сбое
списка перевод считается доступным — объявлять опубликованный материал
непереведённым на основании молчания бэкенда так же недостоверно.
Результат используется для `hreflang`, `x-default`, `noindex` на
непереведённой странице и для заметки `TranslationNotice`.

## C-1. Ограничение длины slug

**Что изменить.** При генерации slug из заголовка ограничить длину
**180 символами** (обрезка по границе слова + при необходимости суффикс
уникальности). Существующие длинные slug'и — перегенерировать с 301-редиректом
со старого адреса.

**Зачем — это не косметика.** В базе есть два материала со slug'ами 247 и 249
символов. Каждый из них:

1. **ронял production-сборку**: имя файла `.next/server/app/ru/news/<slug>.segments`
   выходит за предел **255 байт на компонент пути** (и NTFS, и ext4 — это не
   Windows `MAX_PATH`, его нельзя обойти длинными путями или коротким `distDir`).
   `next build` завершался с `ENOENT: mkdir`;
2. **ломал адресную ревалидацию**: тег `cms:news:<slug>:ru` — 259 символов при
   лимите Next.js в 256, весь набор тегов отвергался с предупреждением в лог;
3. **уже отвергался вебхуком**: `parseRevalidationPayload` проверяет `slug ≤ 180`
   — то есть 180 символов и есть действующая договорённость сторон, просто
   CMS её не соблюдает при генерации.

**Что фронтенд сделал без этого.** `MAX_CMS_SLUG_LENGTH = 180` в
`lib/cache-tags.ts`: длинный slug остаётся рабочим адресом (рендер по запросу),
но исключается из прегенерации и из адресных тегов — один материал больше не
роняет выкладку. Регрессия закрыта `tests/unit/slug-limits.test.ts`.

## C-2. Локализованные подписи пунктов меню

**Что изменить.** `GET /menu` должен отдавать подписи на языке запроса для всех
трёх локалей.

**Зачем.** Сейчас на `/tj` приходит русский фолбэк, на `/en` — пусто.

**Что делает фронтенд.** Подпись из CMS на языке страницы показывается как
есть — в том числе у встроенных разделов (`/news`, `/guides`, …): раньше их
подписи молча подменял словарь, и переименование пункта в CMS на сайт не
попадало. Словарь локали подставляется, только если подпись CMS пуста
(`lib/cms-menu.ts`, шапка и подвал); пункт с пустой подписью и нестандартным
URL отбрасывается; пустое меню — статичная навигация.

**Что для этого нужно от CMS.** Непереведённый пункт должен приходить с
**пустой** подписью, а не с русским фолбэком: `MenuController` сейчас зовёт
`getTranslation('label', $locale, true)`, и на `/tj` такой пункт покажется
по-русски, хотя словарь знает таджикскую подпись. Нужен `false` (без
фолбэка) — или обязательный перевод подписей в редакторе меню.
